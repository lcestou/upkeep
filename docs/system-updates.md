# System updates

The app list can also show the computer's own pending updates: Flatpak apps and runtimes on any system with Flatpak, Snaps where snapd is installed (`snap refresh --list`), Cinnamon's applets, desklets, extensions and themes on any Cinnamon desktop (`cinnamon-spice-updater --list-json`, the list Update Manager shows them from), and the packages the system's package manager would install (security, kernel and driver updates marked as such). The packages come from the first list the system has: Linux Mint's Update Manager (`mintupdate-cli list`), else `apt list --upgradable`, `dnf check-update`, pacman (`checkupdates`, else `pacman -Qu`), or `zypper list-updates`. None needs root. apt, `pacman -Qu` and zypper read the system's last refresh; dnf and `checkupdates` may fetch fresh metadata into a cache of their own. They sit in a folded `System` group at the end of the list, whose subline names the source. On Linux Mint its header has a button that opens Update Manager.

Where fwupd is installed, the group also lists firmware under its own **Firmware** heading: one row per device that `fwupdmgr get-updates --json` names, with the version it has now and the newest release. A device whose new firmware takes effect only after a restart says **Restart needed**. Upkeep only reads what fwupd already knows. It never runs `fwupdmgr refresh`, since fwupd's own timer fetches new metadata. Without fwupdmgr, or when its daemon does not answer (in a container or some VMs), there is no Firmware heading and nothing is said.

The group is off until you turn on **Show system updates** in Settings, under System. The tray number counts only Upkeep's own apps; the tray menu gets a separate "System updates" line instead.

A second switch beneath it, **Install system updates from Upkeep**, is off by default and shows only while the list is on. With it off the group stays read-only. With it on, the rows Upkeep can install get a tick box, and the ticked ones install from the footer's Install button with the ticked apps:

- **Packages from apt without Update Manager** (Ubuntu, Debian and their family), as root: `sudo -n env DEBIAN_FRONTEND=noninteractive apt-get install --only-upgrade -y -o Dpkg::Options::=--force-confdef -o Dpkg::Options::=--force-confold <packages>`. `--only-upgrade` installs nothing that is not there already, and `--force-confold` keeps a config file you edited. A package whose name is a kernel's or NVIDIA's never gets a tick.
- **Packages on Linux Mint**, through Update Manager's own command, as root: `sudo -n mintupdate-cli upgrade -y --keep-configuration -i <list>`. It keeps Mint's rules (dist-upgrade, its blacklist, kernel grouping). `--keep-configuration` is always there, so a config file you edited is never replaced by the package's. `-i` always names the kernel and NVIDIA driver sources (`linux,linux-signed*,linux-meta*,linux-hwe*,nvidia-graphics-drivers-*`) and every package row you did not tick.
- **Flatpak** refs, through `flatpak update -y --noninteractive <refs>`.
- **Snaps**, through `sudo -n snap refresh <names>`.
- **Cinnamon spices**, through `cinnamon-spice-updater --update <type>`. The updater cannot update one spice alone, so a ticked applet installs with every applet that has an update, and the row says so.
- **Firmware**, one device at a time, through `fwupdmgr update <device id> --assume-yes --no-reboot-check --no-metadata-check --no-remote-check --no-unreported-check --no-security-fix --no-device-prompt`. There is no sudo: fwupd's daemon asks polkit itself, so the system's own password window may open. The flags keep `--assume-yes` from saying yes to anything else: no restart at the end, no metadata refresh, no new download remote, no upload of reports and no change to the firmware's security settings. Firmware is refused while the computer runs on its battery (UPower's `OnBattery`), since a flash that loses power can leave a device that does not start. After a firmware update that needs it, the result says "Restart needed to finish the firmware update". Upkeep never restarts the computer; restart when it suits you. A firmware row counts as installed when its command succeeds, since a firmware that waits for the restart can stay listed until then.

Kernel and driver rows never get a tick: both need a restart, and a driver update breaks GPU programs until then, so they stay with the system's own updater. Packages from dnf (`sudo -n dnf upgrade -y --exclude=kernel* --exclude=*nvidia*` with the ticked name.arch, after a trial answered no) and zypper (`sudo -n zypper --non-interactive update --no-recommends` with the ticked name.arch, after a dry run) install like plain apt's: the list is read again first, and a trial (run in the C locale, since its output is read) that fails, removes a package, obsoletes one or names a kernel or NVIDIA package refuses before anything runs as root. pacman's stay read-only, since Arch supports no partial upgrade and a whole `-Syu` would bring the kernel and driver along; with installing on, each such row names the tool that installs it.

With any system row ticked, Install first shows the commands it will run, each as typed, and says which need administrator rights. Nothing runs until you confirm. The system updates go first; the ticked apps install once they finish, or at once if the system install is refused. Then, before any of them, Upkeep checks that sudo works without a password, that nothing holds dpkg's lock, that polkit lets Flatpak update without a dialog, that the package list is still the one you saw, and that a dry run (`mintupdate-cli upgrade -d`, or `apt-get install --only-upgrade --simulate` without Update Manager, no root) names no kernel or NVIDIA package and removes nothing. If any check fails, nothing runs and the group says why. Packages go first, then Flatpak, Snap, Cinnamon and firmware. Each row shows its state while it runs; afterwards the list is read again, a row that is gone is installed and one still listed is failed. Results go to History and the run log.

A System install holds the same lock as an app install, so the two never run together. Closing the window or choosing Quit in the tray waits for it to finish. A background run at login never installs system updates.

## Snapshot before system updates

Where Timeshift or Snapper is set up, a third switch shows under the other two while installing is on: **Take a snapshot before system updates**. It is off until you turn it on. Timeshift counts as set up when `timeshift` is installed and `/etc/timeshift/timeshift.json` names a backup device; Snapper when `snapper` is installed and `/etc/snapper/configs/root` exists. With both, Timeshift is used. The hint under the switch names the tool.

With it on, a System install takes the snapshot after the checks pass and before the first command runs, and the group shows "Taking a snapshot" meanwhile, which can take minutes. The command sheet says a snapshot is taken first. Snapshots need root, so every command below runs through `sudo -n`, as the package commands do. Like the rest of a System install, closing the window or choosing Quit waits for the snapshot to finish.

- **Timeshift**: `sudo -n timeshift --list --scripted` first. When the newest snapshot of any kind (your scheduled daily one too) is under 6 hours old, none is taken and History says which one counts. In btrfs mode a snapshot is always taken, since it costs next to nothing. Otherwise `sudo -n timeshift --create --comments "Upkeep before system updates" --tags O --scripted`. Afterwards Upkeep keeps its own 3 newest: it deletes, with `sudo -n timeshift --delete --snapshot <name> --scripted`, only snapshots whose comment is exactly "Upkeep before system updates". Your own snapshots, and any with another comment, are never touched.
- **Snapper**: `sudo -n snapper -c root create --type pre --print-number --cleanup-algorithm number --description "Upkeep before system updates"` before the commands, and a matching `--type post --pre-number <n>` after them, whether they worked or not. Snapper's own number cleanup removes old pairs, so Upkeep deletes nothing.

If the snapshot fails (sudo wants a password, the backup disk is full, the tool reports an error), Upkeep asks before going on: "The snapshot did not finish: <reason>. Install the system updates anyway?", with **Install anyway** and **Stop**. Stop installs none of the system updates. An ask left unanswered for 30 minutes, or a quit that cannot wait, counts as Stop. History gets a line for the snapshot: the one taken, the one that counted instead, or why there is none.

`upkeep install` on the command line installs Upkeep's apps only, never system updates, so it takes no snapshot.

### Rolling back

- **Timeshift**: open the Timeshift app, pick the snapshot named in History (its comment is "Upkeep before system updates"), and choose Restore. From a terminal: `sudo timeshift --restore --snapshot '<name>'`. A restore of the system replaces system files and needs a restart.
- **Snapper**: `sudo snapper -c root status <pre>..<post>` shows what the updates changed, and `sudo snapper -c root undochange <pre>..<post>` puts those files back. The numbers are in History and the run log. On openSUSE you can also boot into the pre snapshot from the boot menu and run `sudo snapper rollback`.
