# What an install does

1. **Download** to `~/.cache/upkeep/dl`. The size must equal what the release lists, and the SHA-256 must match the asset's digest when the release has one. With no digest, a checksum file in the same release (`SHA256SUMS`, `checksums.txt` and the like, `<file>.sha256`, or electron-builder's `latest-linux.yml`) is read when an update is offered, and the download must match the line naming its file (a private GitHub repo's file is read with your sign-in). Two lines for different folders' copies of the same file name trust neither; a release with no usable line is checked as before. A mismatch fails the install and changes nothing, and the row says you can skip that version. It proves the file arrived whole, not who built it. A redirect from https to plain http is refused. The row's pane, History and `upkeep history` say afterwards which of these checks the download passed. A `zsync:` source lists the size its `.zsync` header gives, and no digest. A `json:` source, a GitLab release and a `links:` page list neither: such a download, with no checksum file beside it, is trusted as the publisher's own answer, over https only, the way its own updater would trust it, and must be at least 1 MiB. The verify probe and the restore point catch a bad one. While another app installs, an `appimage`, `archive`, `file`, `deb` or `rpm` app further back in the run downloads ahead, two at a time, unless that would leave less than 5 GiB free on the disk. At its turn the file is read back and checked again, and downloaded afresh if it no longer matches. A source build, a command app, and any app whose table has `serve` or `pause` download at their turn, as before.

   **Can it run here?** Before the restore point, Upkeep reads the headers of each new program without running it: a `file` or `appimage` app's download, and each `bins` program of an `archive`, which is now unpacked into the cache before the restore point. It refuses the install, with nothing changed, when the program's loader (`PT_INTERP`, such as musl's `/lib/ld-musl-x86_64.so.1` on a glibc system) is not on this system, when it needs a newer glibc than `getconf GNU_LIBC_VERSION` reports, or when its x86-64 level note (`X86_ISA_1_NEEDED`) asks for more than the CPU's flags in `/proc/cpuinfo` give (v2, v3, v4). The row says why, for example "Bat 0.25.0 needs glibc 2.39; this system has 2.35, so nothing was installed." The next check offers that version again unless you skip it. A file that is not ELF or cannot be read, a static program, and a question this system cannot answer (no `getconf` on musl, no CPU flags) pass as before. Only headers are read: the program inside an AppImage's squashfs is not, so an AppImage is checked by its runtime alone, and a library loaded late is not seen. `.deb` and `.rpm` files are left to the package tool. The verify step below stays the real judge.

2. **Back up** the files about to be replaced into `~/.local/share/upkeep/backups/<app>/<version>/`. This is the restore point. A `.deb` keeps the installed version's package, taken from that version's release (or its `links:` page), and goes back with `dpkg -i`; an `.rpm` does the same through `rpm -U --oldpackage`. A self-updating app keeps one when its table has `restore`, a command with `{version}` (and `{tag}`) that installs a given version, such as `["bun", "add", "-g", "wrangler@{version}"]`. A source app with `dir` or `stage` keeps its checkout's commit, the files its table names and the files it replaces; one built in a fresh clone keeps none. "Restore points to keep" in Settings applies to all of them. With more than one kept, every point but the newest is packed into one zstd tarball inside its folder once an update succeeds, or a restore that keeps a point of the version it replaces (a source build's restore keeps none, so its older points wait for the next update), which halves a source build's kept trees; the newest stays plain, so a rollback right after a failed start is still a rename. AppImages, packages and points that would not shrink by a tenth stay plain, and so does every point when `tar` cannot use `zstd`. Restoring a packed point unpacks it beside itself first. A table with `keep_with_restore` also has those settings copied into the point. A restore from the window puts them back with the app, and so does a rollback after the new version ran (see [the app list](app-list.md)).
3. **Install.** The new file is written beside the old one and renamed into place, so a running copy keeps working and a full disk leaves the old file whole. A running app is not closed. Its row says "Restart to apply". When its table has `restart` or `relaunch`, its pane offers Restart now and the "Restart to finish" group a button that restarts every such app; one that would close a window asks first, since unsaved work in it is lost.
4. **Verify.** The version probe runs again. If the new copy will not start, the restore point goes back and the row says so.

While a run installs, from its start to its end, Upkeep asks logind to hold sleep (`systemd-inhibit --what=sleep --mode=block`), so an idle timer or the menu's Suspend does not land between the restore point and the verify. Shutdown is never held, and closing the lid still suspends under logind's default `LidSwitchIgnoreInhibited=yes`. The lock is a child process tied to Upkeep's own (`tail --pid`), so it goes when the run ends or stops, and within a second if Upkeep crashes. A system without `systemd-inhibit` installs without it, and the run log says so once.

A source build reads, when the check offers it, the commit its tag points at (`git ls-remote`, against the checkout's `origin` for a `dir` row or the repo for a clone). After the clone or the fetch, the tag must still point at that commit; if it moved, the build fails before any step runs or any restore point is taken, the run log names both commits, and the row says to check again. A tag moved between check and install is how a repointed release slips in. When the remote did not answer at check time, the build goes on as before.

Root steps use `sudo -n`. If sudo wants a password the app fails with a message and nothing is changed.

## Stop now

Stop now ends a run while an app is installing. The app goes back to how it was and the apps behind it do not start.

- A step Upkeep can end safely is cut: a download, unpacking into the cache, a `git clone` or `fetch`, a built app's build steps and `check_built`, its start tests and health checks, the version probe, a service stop or start that does not run as root, and a self-updating tool's `update` command. A cut step gets TERM to its whole process group, then KILL five seconds later.
- A step Upkeep cannot end safely is waited out: `dpkg -i`, `rpm -U`, anything under `sudo` (sudo cannot pass a KILL on to the root command, so cutting it would only orphan the command), a source build in a fresh clone, the step that puts a built app's files in place, and every undo. The row says what it waits for: "Waiting for dpkg to finish, then putting 1.4.2 back."
- Claude Code plugins are updated one at a time; Stop now lets the one in progress finish and skips the rest.
- Then the app's own failure path runs: the restore point goes back and the row says "Stopped. 1.4.2 is back in place." A self-updating tool with no `restore` command has no point to put back, so its update is interrupted and the row says what the tool reports after: "Stopped. wrangler still reports 4.157.0.", or that it does not start.
- Once a built app's verify has passed, the rest of its finish (pruning, packing older points) is waited out and the update stays.

While an app installs, a row whose step has printed nothing for two minutes says so, with the step's own time limit beside it: "No output for 3 min. It stops on its own in 7 min." Many steps (unpacking, copying, `git fetch`, a health check) print nothing as they work, so the line only states the two times. It never stops anything by itself.

## Where things live

| Path                                  | Holds                                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------ |
| `~/.config/upkeep/apps.toml`          | the app list                                                                               |
| `~/.local/state/upkeep/state.json`    | skipped versions, held and paused apps, automatic installs, pre-release switches, settings |
| `~/.local/state/upkeep/logs/`         | one log per run, the newest 50                                                             |
| `~/.local/share/upkeep/history.jsonl` | every install and cleanup, append-only                                                     |
| `~/.local/share/upkeep/backups/`      | restore points                                                                             |
| `~/.cache/upkeep/`                    | release lookups, downloads, source clones, the last check's rows. Safe to delete.          |
